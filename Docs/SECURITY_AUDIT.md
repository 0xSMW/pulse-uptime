# Security audit entry points

This is the static entry-point register for the current checkout. It records **95 HTTP operations in 78 route files**, plus **four Server Actions**. The v1 inventory is checked against OpenAPI by `openapi/service.openapi.test.ts`; `app/entry-points.test.ts` checks the 21 other HTTP operations and the four actions across `app`, `components`, and `lib`. Route inventory is a starting point for tracing input to privilege and execution sinks, not proof that an operation is secure.

## Reading the register

- **Credential:** `public` needs no credential; `bootstrap` requires the operator-held setup token before first-admin creation; `human` requires a dashboard session; `authenticated` accepts a human session, API token, or CLI session as allowed by the middleware; `cron` requires `CRON_SECRET`; `signed` requires the Porkbun webhook signature. A user-held session mutation also requires an allowed Origin.
- **Verification:** `R` means a direct route test exists, `S` means relevant downstream service tests exist, and `I` means the mechanical inventory check is the only check called out here. These labels do not certify complete negative-path coverage. The route tests for several groups mock downstream services.
- **Input:** path parameters, query parameters, JSON bodies, multipart uploads, cookies, bearer headers, and server action arguments are all untrusted. A `read` below can still disclose data or trigger a bounded probe; a `write` can affect monitoring, notifications, credentials, or publication.

## `/api/v1` HTTP operations — 74

The credential and scope checks are performed in `lib/api/middleware.ts`; the OpenAPI operation declares the same scope. `GET` and `POST` on a collection are listed separately because their privileges and effects differ.

## Audit sequence

1. Trace each public or pre-auth input through bootstrap, invite, device authorization, signed webhook and readiness flows into the first privileged state change. Exercise races, replay, malformed and oversized inputs, revoked credentials, and source-IP spoofing.
2. Keep both HTTP admission matrices and the direct action tests current. Extend stateful denial checks to stale/revoked/expired credentials, valid bootstrap/cron/webhook transitions, and concurrent revocation.
3. Trace accepted low-privilege input to outbound fetches, parsers, HTML/CSS, SQL, files and process execution. Test redirects, DNS rebinding/metadata IPs, decompression and body limits, and stored content rendered on public pages where applicable.
4. Exercise state transitions with real services/transactions for token issuance, admin creation, invites, config apply, incident exclusion, webhook receipt and cron handoff. Assert denial before side effects and failure without partial privileged state.

## Current findings and next hardening pass

- **Closed privilege paths:** invite creation and team writes now recheck the live actor under transaction locks; demotion, removal, token/CLI revocation, and credential rotation revoke pending invites from the affected credential tree. Explicit Security-page session revocation also revokes credentials issued under that exact session, including descendant API tokens and pending invites. Bootstrap readiness requires the operator token before provider side effects. The password and email change triggers cover older application instances during rollout. Real PostgreSQL regressions exercise the invite and credential transitions.
- **Closed execution and exfiltration paths:** Next.js and vulnerable production dependencies were updated; credentialed Porkbun requests and provider probes now handle redirects manually; image uploads cap the full streamed multipart body before parsing. Local two-server tests verify redirect targets do not receive Porkbun headers. Static source review found no untrusted shell/eval execution path in application handlers.
- **Temporal authorization:** monitor/group writes, monitor pause/resume/test, dependency and report writes, incident exclusions, configuration and domain-monitoring writes, health refresh, test-notification enqueue, image insertion, token creation, privileged credential revocation, CLI device approval/denial, the first-monitor site probe and activation writes, and onboarding completion now recheck live authority at their mutation or outbound-effect boundary. Self-account operations and CLI self-revocation use narrower ownership/session checks described below. A route's initial admission check cannot settle a demotion or revocation that happens while its request body or a probe is pending. Completed idempotency replays bypass the mutation callback, so review their response sensitivity separately.
- **Admission coverage and remaining evidence:** `app/v1-authorization-matrix.test.ts` loads every v1 route export and runs all 71 authenticated operations through the real middleware with anonymous, viewer, admin, scoped/unscoped API token and CLI principal, unresolved principal, and cross-origin human cases. It stops accepted calls immediately after middleware, then separately exercises eight human-only route guards with machine credentials. `app/non-v1-admission-matrix.test.ts` loads all 21 other HTTP operations and checks their relevant negative boundary: cross-origin public mutations, anonymous/cross-origin onboarding writes, viewer denial of admin onboarding probes, missing/wrong bootstrap token, missing/wrong cron bearer, unsigned webhook, and anonymous public reads. Direct tests for the three CLI actions deny anonymous/viewer calls before service work and forward admin calls; the public report action tests enforce source rate limiting and published-only reads. The v1 stale/revoked/expired rows simulate failed principal lookup, and the non-v1 matrix stops at denial or a stubbed public data source. These tests do not prove database credential predicates, valid signed webhook or cron side effects, live service authorization, or transaction race behavior. Exercise those with real credential/session rows and concurrent revocation. Keep inventory and OpenAPI tests as change detectors, not service-level authorization evidence.
- **Dependency watch:** the high/critical npm advisory gate and reachable Go vulnerability gate now fail CI; three moderate/low npm advisories remain in development-only lint tooling. Reassess them when its compatible release line is available.

## Temporal authorization checklist

This checklist covers all 51 non-GET `/api/v1` operations: 48 state-changing and three read-like POSTs (configuration validate/plan and exclusion preview). `atomic` means the database mutation and idempotency completion share a transaction; `conservative` and `replay_safe` complete afterward; `direct` has no idempotency wrapper. The first authenticated check is in `authorize()` unless stated otherwise. “Live” means the acting credential and required scope are checked again under locks held through the relevant mutation. A stored idempotency replay does not enter the mutation callback. Treat entries marked “route only” as race candidates, not as demonstrated privilege escalation.

- **Public device grant:** `POST /cli-auth/device`, `POST /cli-auth/token` — public, atomic; create a pending request or exchange an approved code for a CLI credential. The exchange validates the code, installation and owner state in its service. Verify concurrent approval, revocation and repeated polling with a real database.
- **Credential issuance:** `POST /tokens` — `tokens:manage`, atomic; live creator check and scoped token insert in the transaction. A human-issued token records its exact issuing session; completed replay rechecks the exact creator and child before returning the derived bearer secret. `POST /users/invites` — `users:manage`, atomic; service rechecks the actor under team/credential locks before issuing an invitation, recording the exact issuing session for a human actor. `PATCH /users/{userId}`, `DELETE /users/{userId}` — `users:manage`, conservative; team service rechecks the actor under locks before role change or removal. CLI approval records the authorizing human session on the installation; reapproval retires earlier CLI sessions and descendants before moving that provenance.
- **Credential revocation:** `DELETE /tokens/{tokenId}`, `DELETE /users/invites/{inviteId}`, `DELETE /cli-auth/installations/{installationId}`, `POST /cli-auth/installations/revoke-all` — `tokens:manage` or `users:manage`, atomic; live actor check in the transaction before service revocation. The last operation can revoke all machine credentials. `POST /cli-auth/revoke` — authenticated CLI installation or validated self-revoke replay, atomic; service resolves and revokes its own installation, without a separate live actor check in the mutation.
- **Configuration:** `POST /config/validate`, `POST /config/plan` — `config:write`, direct, read-like validation/planning; no persisted write. `POST /config/apply` — `config:write`, replay_safe; service rechecks live scope under team then machine locks before the configuration lock and Edge Config write, with an 8-second outbound timeout, then records the operation. `PUT /status-page-config` — `config:write`, atomic; live check before database document update, followed by cache revalidation after commit.
- **Monitor and group registry:** `POST /monitors`, `PATCH /monitors/{monitorId}`, `DELETE /monitors/{monitorId}`, `POST /groups`, `PATCH /groups/{groupId}`, `DELETE /groups/{groupId}` — `monitors:write`, atomic; shared helper rechecks live scope inside the transaction before database mutation. `POST /monitors/{monitorId}/pause`, `POST /monitors/{monitorId}/resume` — `monitors:write`, atomic; their shared handler also rechecks live scope before scheduler state change. `POST /monitors/{monitorId}/test` — `monitors:write`, conservative; live scope is checked in a transaction held through the external probe.
- **Incident exclusions:** `POST /incidents/{incidentId}/exclusions/preview` — `monitors:write`, direct, read-like preview. `POST /incidents/{incidentId}/exclusions`, `POST /incidents/{incidentId}/exclusions/{exclusionId}/undo` — `monitors:write`, atomic; shared helper rechecks live scope before database change, with cache revalidation after commit.
- **Dependencies:** `POST /dependencies`, `PATCH /dependencies/{dependencyId}`, `DELETE /dependencies/{dependencyId}`, `POST /dependencies/{dependencyId}/refresh`, `POST /dependencies/{dependencyId}/backfill` — `dependencies:write`, atomic; live scope is checked in each transaction before registry change, refresh scheduling or historical backfill. The scheduled poll performs outbound fetch later under cron authority.
- **Public reports:** `POST /status-reports`, `PATCH /status-reports/{reportId}`, `DELETE /status-reports/{reportId}`, `POST /status-reports/{reportId}/publish`, `POST /status-reports/{reportId}/updates`, `PATCH /status-reports/{reportId}/updates/{updateId}`, `DELETE /status-reports/{reportId}/updates/{updateId}`, `POST /incidents/{incidentId}/promote` — `reports:write`, atomic; shared report helper rechecks live scope in the transaction before database change or publication. Public cache paths are revalidated after commit.
- **Own account:** `PATCH /me`, `POST /me/email`, `POST /me/password`, `DELETE /me/sessions/{sessionId}`, `POST /me/sessions/revoke-others` — human session, direct. All five recheck and lock the exact acting session inside their write transaction; email and password changes additionally require the current password and use compare-and-swap. Explicit revocation of one or all other sessions cascades to API tokens issued by those sessions, CLI installations authorized by them, their CLI sessions and descendant tokens, and pending invites in those credential trees, in the same transaction. No cross-user privilege is delegated.
- **System and outbound effects:** `POST /database-health/refresh`, `POST /domain-monitoring/check`, `POST /domain-monitoring/webhook` — `config:write`, conservative; each opens a transaction, rechecks live scope, and holds the authority locks through health refresh, Porkbun connection check or provider webhook management. `PATCH /domain-monitoring/settings` — `config:write`, atomic; live check before the settings update. `POST /notifications/test` — `notifications:test`, atomic; live check before transactional outbox enqueue, then background delivery. `POST /images` — human avatar or `config:write` branding, direct; full multipart body is capped before parse, then the image insert transaction rechecks live scope before persisting bytes.

For non-v1 writes, the first-admin bootstrap and invite acceptance services take transaction locks and derive authority from the live token/record. CLI device approval and denial recheck and lock the exact admin session in their service transactions. First-monitor activation checks the admin session under a held transaction during its bounded site probe, then checks again before configuration and Edge Config writes; database-backed probe admission and readiness run before that held transaction to avoid connection-pool starvation. Onboarding completion rechecks its acting human session before progress writes. Onboarding draft/back writes and the verify/readiness probes still rely on admission-time session or bootstrap checks. An in-flight fixed-provider readiness call or own-progress write can finish after revocation; the readiness call can PATCH its Edge Config sentinel or send a test email, but cannot probe a user-supplied site URL after revocation. No role grant or shell execution was identified in those paths. Cron jobs and the Porkbun webhook use fixed secret/signature admission rather than a revocable user principal. Test remaining races by pausing after route admission, changing the actor's role or credential in another transaction, resuming, and asserting the intended state and outbound effects; reverse the ordering to verify an already committed write remains valid.

**Legacy provenance limit:** migrations `0034` and `0035` add nullable session IDs without backfilling existing invites, API tokens, or CLI installations. A NULL row cannot be assigned to one revoked human session, so exact-session cleanup does not select it by provenance. Existing broader user-level credential rotation, demotion/removal and explicit token/installation revocation remain the containment paths. Ordinary logout revokes the human session only; the cascade above applies to the explicit `/me/sessions` revocation operations.
